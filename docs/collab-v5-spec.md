## 0. One-paragraph model

The host (an oms TUI) is authoritative. Guests never talk to each other. All parties connect to a dumb WebSocket **relay**: the host connects with `?role=host` and guests with `?role=guest`, both to `/r/<roomId>`. Every application message is a **BINARY** WebSocket frame laid out as `[u32 BE peerId][12B IV][AES-256-GCM ciphertext || 16B tag]`. The plaintext is a UTF-8 JSON object with a `t` discriminator. The relay only routes frames and sends a few unencrypted **TEXT** JSON control messages. A guest sends `hello`. The host replies with a targeted `welcome`, then `snapshot-chunk` frames carrying the transcript, released as the guest acknowledges them with `snapshot-ack`, then broadcasts live `entry`/`event`/`stream`/`stream-delta`/`state`/`agents`/`bus` frames. Guests holding a full link (one with a write token) can also send `prompt`/`abort`/`ui-response`/`agent-cmd`, and run an allowlisted set of host slash commands (`command`, §5.2a).

## 1. Links

### 1.1 Secret layout

| Part | Bytes | Encoding in link | Meaning |
|---|---|---|---|
| roomId | 16 random bytes → base64url, no padding = **22 chars** (`proto:239-243`, `wire:437`) | regex `[A-Za-z0-9_-]{10,64}` (`proto:235-236`) | relay routing id |
| room key | 32 (`wire:440`) | first 32 bytes of secret | AES-256-GCM key |
| write token | 16 (`wire:447`) | bytes 32..47 of secret, **full links only** | proves prompt/abort/answer capability |
| secret text | 32 bytes → **43 chars** (view-only link); 48 bytes → **64 chars** (full link) | base64url (RFC 4648 §5, `-`/`_`), **no `=` padding**, regex `^[A-Za-z0-9_-]+$` (`proto:237`) | `base64url(key ∥ writeToken)` for full links, `base64url(key)` for view links (`proto:289-290`) |

The parser decodes the secret and requires exactly 32 or 48 bytes. Any other length is an error: `"Collab link key must be 32 (view) or 48 (full) base64url bytes"` (`proto:378-381`). Key = bytes `[0,32)`. Write token = bytes `[32,48)` when present (`proto:382-383`).

**base64url detail.** The native parser uses Node's lenient `Buffer.from(s,"base64url")` (`proto:378`). The browser parser pads the string and calls `atob`, which rejects a length ≡ 1 mod 4 (`wlink:38-51`). For Kotlin, require the regex above plus a length of exactly 43 or 64 characters. Then decode with `java.util.Base64.getUrlDecoder()`, which accepts missing padding. Valid links are identical under both decoders.

**The write token in `hello`** is the 16 token bytes **re-encoded** as base64url without padding (22 chars). You cannot take a substring of the secret text, because 32 bytes do not end on a character boundary (`wclient:234`). The host decodes it, checks the length is 16, and compares in constant time (`host:927-932`).

### 1.2 Accepted link forms

(`docs/collab.md:113-146`, `proto:340-385`)

| # | Form | Relay WS base | Notes |
|---|---|---|---|
| 1 | `<roomId>.<secret>` | `wss://my.omp.sh` (default relay, `wire:450`) | Canonical output for the default relay (`proto:291`) |
| 2 | `<roomId>#<secret>` | default relay | Legacy |
| 3 | `host[:port][/prefix]/r/<roomId>.<secret>` | `wss://host[:port][/prefix]` | No scheme means `wss://` is assumed. This is the canonical output for custom `wss` relays (`proto:292-295`) |
| 4 | `host[:port][/prefix]/r/<roomId>#<secret>` | same as 3 | Legacy |
| 5 | `wss://…/r/<roomId>.<secret>` / `ws://…/r/<roomId>.<secret>` | as written | `ws://` relays always print with the scheme (`proto:292-294`) |
| 6 | `https://…/r/<roomId>.<secret>` → `wss://`; `http://…` → `ws://` | normalized | `proto:254-265` |
| 7 | `http(s)://web-host[/path]/#<any link above>` | from the **fragment** | Browser deep link. The fragment wins when it parses (`proto:355-359`) |
| 8 | `https://relay/r/<roomId>#<secret>` | `wss://relay` | Legacy. Used when the fragment alone is not a complete link (fallback, `proto:360-384`) |
| 9 | Any of the above with `%23` in place of `#` | | `%23` is replaced by `#` (case-insensitive) before parsing (`proto:343`) |
| 10 | Scheme-less browser wrapper `my.omp.sh/#<roomId>.<secret>` | from fragment | becomes `wss://my.omp.sh/#…`, path does not match, so the fragment is parsed recursively (`proto:363-369`) |

Rejected inputs: any scheme other than ws/wss/http/https (for example `ftp://`), a missing `/r/<roomId>`, and a secret of the wrong length.

### 1.3 Parse algorithm

Implement this exactly. It is a string-level port of `proto:340-385` and `proto:246-269`. The JS uses the WHATWG `URL` parser, so the URL-model rules it relies on are listed after the pseudocode.

```
DEFAULT = "wss://my.omp.sh"
ROOM_PATH = ^(.*)/r/([A-Za-z0-9_-]{10,64})(?:\.([A-Za-z0-9_-]+))?$
BARE      = ^([A-Za-z0-9_-]{10,64})[#.]([A-Za-z0-9_-]+)$
HAS_SCHEME= ^[A-Za-z][A-Za-z0-9+.-]*://

parse(link):
  text = link.trim().replaceAll("%23" (case-insensitive), "#")
  if BARE matches text:      text = DEFAULT + "/r/" + g1 + "." + g2
  elif not HAS_SCHEME(text): text = "wss://" + text
  url = parseUrl(text) or return error("Invalid collab link: …")
  frag = url.fragment                      // text after the FIRST '#', "" if none
  if url.scheme in {http,https} and frag != "":
      r = parse(frag); if r is ok: return r      // the fragment wins
  m = ROOM_PATH.match(url.path)                 // url.path: percent-encoded path, "/" if empty
  base = normalizeRelay(url.scheme, url.host, url.port, m ? m.g1 : "")
  if base is error: return base                 // "Unsupported relay URL scheme: ftp:"
  if m is null:
      if frag != "" and url.scheme not in {http,https}: return parse(frag)
      return error("Collab link must contain a /r/<roomId> path")
  roomId = m.g2
  secretText = m.g3 ?: frag
  if secretText == "": return error("Collab link is missing the <key> part")
  secret = base64urlDecode(secretText) // must match ^[A-Za-z0-9_-]+$
  if secret.size not in {32,48}: return error("Collab link key must be 32 (view) or 48 (full) base64url bytes")
  return { wsUrl = base + "/r/" + roomId, roomId,
           key = secret[0..32), writeToken = secret.size==48 ? secret[32..48) : null }

normalizeRelay(scheme, host, port, path):
  wsScheme = {wss,https} -> "wss" ; {ws,http} -> "ws" ; else error "Unsupported relay URL scheme: <scheme>:"
  portPart = (port present and not the scheme default) ? ":" + port : ""
  return wsScheme + "://" + host + portPart + path.trimEnd('/')     // strip ALL trailing slashes
```

WHATWG URL rules to replicate:

- Lowercase the scheme and the host (`https://Relay.Example.com` becomes `relay.example.com`).
- Drop default ports: 443 for wss/https and 80 for ws/http. `wss://h:443/…` becomes `wss://h/…`.
- `url.port` is the port of the *outer* URL. A default port for the outer scheme counts as "no port", even though the result's scheme may differ. For example, `http://h:80` becomes `ws://h`.
- Keep IPv6 hosts bracketed (`[::1]`).
- Ignore userinfo and query.
- The fragment is everything after the first `#`, including any later `#` characters.
- **(inferred)** Using OkHttp `HttpUrl` after mapping ws→http and wss→https works for host and port normalization, but extract the fragment by hand (split at the first `#`).

**Connect URL** = `wsUrl + "?role=guest"` (`wsock:112`, `rc:506`).

### 1.5 What `/collab` prints, the QR code, and `collab.webUrl`

The `/collab` output is built in `packages/coding-agent/src/slash-commands/builtin-collaboration.ts:29-69`:

- It always prints the native invite `oms join "<link>"`, where `<link>` is the compact form from `formatCollabLink`, i.e. forms 1, 3 or 5 (`:33`). `/collab view` prints the view link, which has no token (`:31`).
- It prints a browser line **and a QR code only when the browser link (`webLink`) is non-null** (`:38-45`, `:65-69`). `webLink = formatCollabWebLink(relay, …, webUrl)` (`proto:328-338`):
  - `collab.webUrl` empty and relay = `wss://my.omp.sh`: `https://my.omp.sh/#<roomId>.<secret>`
  - `collab.webUrl` empty and any other relay: **null**. The output is native-only, with no QR code.
  - `collab.webUrl` set (must be http/https with no query or fragment, `proto:306-319`): `<webUrl without trailing slashes>/#<compact relay link>`. For example `http://10.66.66.8/#ws://10.66.66.8/r/<id>.<secret>`.
- The QR code encodes **exactly the `webLink` string**, in byte mode at EC level M (`packages/tui/src/chrome/collab-qrcode.ts:41-46`). Feed a scanned QR straight to `parse()`. It is always form 7.
- `collab.webUrl` only changes the browser invitation and QR. It does not move the relay (`docs/collab.md:139,183`). The other settings are listed in `packages/coding-agent/src/collab/settings.ts:9-72`: `relayUrl`, `webUrl`, `displayName`, `autoStart`.
- **(inferred)** For custom relays without `webUrl`, users only have the text `oms join "<link>"`. Strip an `oms join "…"` wrapper before parsing pasted text. The parser itself does not accept that wrapper.

## 2. Transport

### 2.1 Opening the socket

- Use a plain WebSocket GET to `<wsUrl>?role=guest`. There is no subprotocol, no custom header, and no auth header (`wsock:112`; `rc:506-510`, which adds only an HTTP proxy option).
- The browser sends `Origin` automatically. **Unknown:** whether the production relay checks `Origin`, because its source is not in this repo. The reference relay ignores it (`relay:51-61`).
- The relay accepts the upgrade only when the path is exactly `/r/<roomId>` (any prefix is handled by a reverse proxy) and `role` is `host` or `guest`. Otherwise it returns HTTP 404 (`relay:20,51-60`).
- A guest joining a room with no host is **accepted, then closed with 4004** (`relay:73-77`).
- `ws://` URLs need cleartext traffic allowed in the Android network security config **(inferred)**.

### 2.2 Binary envelope

(`wire:434-435`, `proto:207-224`, `relay:83-100`)

```
offset 0..3   u32 big-endian peerId
offset 4..    sealed = [12B IV][ciphertext][16B GCM tag]
```

| Direction | peerId on the wire | Relay behaviour |
|---|---|---|
| guest → relay | **always 0** (`wlink:7-8`, `wsock:72`) | Rewrites bytes 0..3 to the sender's peer id, then forwards to the host (`relay:97-99`) |
| host → relay | 0 = broadcast; N = only to guest N | Forwards **unchanged** (`relay:87-95`) |
| relay → guest | 0 for broadcasts, or **your own peer id** for targeted frames (welcome, snapshot, errors, replies) | |

Guests may ignore the peerId on receipt. An envelope shorter than 4 bytes is ignored (`proto:220-224`). Guests must send BINARY frames: the relay ignores TEXT from clients (`relay:84`). Peer ids start at 1 for each room *instance* (`relay:70,78`).

### 2.3 Relay control messages

These are TEXT frames carrying unencrypted JSON (`wire:467-472`, `relay:12-14,101-120`).

| To | Message | When |
|---|---|---|
| host only | `{"t":"peer-joined","peer":N}` / `{"t":"peer-left","peer":N}` | A guest connects or disconnects |
| guest | `{"t":"room-closed"}` | The host socket closed. **Followed immediately by close code 4001** |

Guests can ignore all TEXT frames. The browser client never wires `onControl` (`wclient:236-238`) and relies on the close code instead. Malformed TEXT is ignored (`wsock:137-144`).

### 2.4 Close codes

(`wsock:13-18`, `rc:18-23`, `wsock:175-194`)

| Code | Reason string | Guest action (web + native) |
|---|---|---|
| 4001 | room closed | Host dropped. **Reconnect with backoff**, and set `retryMissingRoom = true` (the host usually reconnects to the *same* roomId within seconds) |
| 4004 | no such room | **Fatal on first connect.** Retry only if `retryMissingRoom` is set, i.e. after a 4001 |
| 4009 | a host is already connected | Host-only; never sent to guests |
| 4029 | room is full | Fatal. Stop |
| 1000 | (normal) | Sent by the client for an intentional close |
| anything else (1006, 1001, network errors, …) | `connection lost (code N)` | Transient. Reconnect with backoff |

`retryMissingRoom` resets to false as soon as **any** frame decrypts successfully (`wsock:166-167`). A decryption failure (bad key or corrupted frame) is **fatal**: close 1000 and never reconnect (`wsock:159-163,197-212`; `rc:653-654`).

### 2.5 Keepalive

- **Native oms clients** (host and native guest) send **WebSocket protocol PING frames** every **15 s**. They drop and reconnect when nothing has been received, pongs included, for **40 s** (`rc:57-59,533-535,555-583`). The silent socket is terminated and handled like close 1006 with reason `"relay stopped responding"`.
- **Browser guests send no keepalive at all.** Browsers cannot send ping frames, and there is no application-level ping message in the protocol.
- **(inferred)** The relay therefore tolerates silent guests. The reference relay runs on Bun, whose WebSocket server has an idle timeout and automatic server pings. A code comment says the public relay retired a silent connection after about 40 s (`rc:28-35`).
- **Android recommendation:** OkHttp `pingInterval(15, SECONDS)`. OkHttp fails the socket if a pong is missed, which gives behaviour equivalent to the native client.

### 2.6 Reconnect behaviour

Both clients use the same backoff (`wsock:20-23,214-223`; `rc:25-26,764-772`):

```
delay = min(1000 * 2^attempt, 30000) * uniform(0.75, 1.25)  ms;  attempt++
attempt resets to 0: on open (unless retryMissingRoom) and whenever a frame decrypts OK
```

The behaviour on each reconnect is the same in both clients:

1. On every successful open, send a **fresh `hello`** (`wclient:336-347`, `nguest:362-378`).
2. Drop any partially received snapshot and the stream baseline (`wclient:349-363`, `nguest:367-371`).
3. Keep showing the old transcript until the new snapshot completes. The new `welcome` + chunks replace it (`wclient:470-472`).
4. After a successful join, neither client gives up on its own: no welcome timer is re-armed, so the client retries until a `bye`, a fatal close, or the user leaves. **(inferred)** Android should show a "reconnecting…" state with a manual Leave button.

**Send buffering:**

- The browser buffers up to 256 sealed envelopes while disconnected and flushes them **before** the new `hello` (`wsock:23,83-84,118-119`).
- **Do not copy this.** The host maps permissions per peer id, and a reconnect yields a new id. A buffered `prompt`/`abort`/`ui-response`/`agent-cmd` arriving before `hello` is rejected with `error "<action> is disabled on a read-only link"`, where the action is `prompting`, `interrupting`, `responding to ask` or `agent control` (`host:935-937,1204-1206,1254-1259,1306-1310,1428-1430`). Because that error arrives before `welcome`, the browser treats it as fatal (`wclient:658-666`).
- **(inferred)** The browser avoids this only because its UI disables input unless the phase is `live`. Android should enable user actions only in the `live` phase and drop or re-queue them otherwise.

### 2.7 Ordering

- Seal and send in call order through a single serialized queue (`wsock:49-50,73-88`).
- Decrypt and apply received frames strictly in arrival order through a single serialized chain (`wsock:51-52,155-172`).
- The protocol depends on that order: `welcome` → chunks → stream baseline → live frames.

## 3. Crypto

### 3.1 Sealed layout

(`crypto:1-57`, `wcodec:1-72`)

| Item | Value |
|---|---|
| Cipher | AES-256-GCM, raw 32-byte key from the link (`crypto:27-31`) |
| IV | **12 bytes**, freshly random for **every** frame (`crypto:11,38-41`) |
| Tag | **16 bytes** (128-bit, the WebCrypto default), **appended** to the ciphertext |
| AAD | **none** |
| Plaintext | `UTF-8(JSON.stringify(frame))`: one JSON object, no trailing newline (`crypto:34-41`) |
| Sealed | `IV(12) ∥ ciphertext ∥ tag(16)`, so `len = 28 + len(plaintext)` |
| Open | reject if `len ≤ 12` (`crypto:51-53`), else decrypt `bytes[12..]` with `IV = bytes[0..12)` |
| Auth failure | guest: fatal, never reconnect. Host: silently drops undecryptable guest frames (`rc:651-655`) |

The browser has a pure-JS fallback (`@noble/ciphers` gcm) that produces byte-identical output (`wcodec:192,219-247`).

### 3.2 Kotlin (`javax.crypto`)

Java's GCM output is already `ciphertext ∥ tag`, which matches the wire.

```kotlin
private val rng = java.security.SecureRandom()

fun seal(key: ByteArray /*32*/, json: String): ByteArray {
    val iv = ByteArray(12).also(rng::nextBytes)            // NEVER reuse an IV
    val c = Cipher.getInstance("AES/GCM/NoPadding")
    c.init(Cipher.ENCRYPT_MODE, SecretKeySpec(key, "AES"), GCMParameterSpec(128, iv))
    return iv + c.doFinal(json.toByteArray(Charsets.UTF_8))
}

fun open(key: ByteArray, sealed: ByteArray): String {
    require(sealed.size > 12) { "Sealed frame too short" }
    val c = Cipher.getInstance("AES/GCM/NoPadding")
    c.init(Cipher.DECRYPT_MODE, SecretKeySpec(key, "AES"), GCMParameterSpec(128, sealed, 0, 12))
    return String(c.doFinal(sealed, 12, sealed.size - 12), Charsets.UTF_8) // throws AEADBadTagException
}

fun envelope(sealed: ByteArray): ByteArray =
    java.nio.ByteBuffer.allocate(4 + sealed.size).putInt(0).put(sealed).array()  // BE by default

fun unpack(b: ByteArray): Pair<Long, ByteArray>? =
    if (b.size < 4) null
    else (java.nio.ByteBuffer.wrap(b, 0, 4).int.toLong() and 0xFFFFFFFFL) to b.copyOfRange(4, b.size)
```

Create a new `Cipher.init` for each frame. Java refuses to reuse a key+IV pair on one GCM instance.

### 3.3 JSON encoding rules for the Kotlin side

- `kotlinx.serialization`: set `ignoreUnknownKeys = true`, `explicitNulls = false`, and `encodeDefaults = false`.
- **Omit** absent optional fields. Never send `null`. Specific cases:
  - `ui-response.value` on cancel: omit it (`Composer.tsx:193`).
  - `hello.writeToken` on a view link: omit it (`wclient:341`).
  - `prompt.images` when empty: omit it (`nguest:469`).
- Host consequences of a `null` instead of an omitted field:
  - `null` value on an approval: works out as Deny.
  - `null` value on an ask: treated as cancel.
  - `null` on a generic extension select: it receives `null` instead of `undefined`.
- **(inferred)** Use Long for every timestamp, counter and offset, and Double for `percent` and `cost`.
- Receivers must ignore unknown `t` values, unknown entry types, unknown event types, and unknown content block types. Every reference switch has a tolerant `default` (`wire:9-12`, `wclient:669-671`).

### 3.4 Test vectors

**V1: guest hello (full link, paged history)**

## 4. Handshake and session lifecycle

### 4.1 Sequence

```
guest                                   relay                           host
  |--- WS GET /r/<id>?role=guest ------->|  (4004 if no host)             |
  |                                      |--- TEXT peer-joined{N} ------->|
  |=== hello (sealed, peerId 0) ========>|=== (peerId rewritten to N) ===>|
  |<== welcome (targeted N) =============|<===============================|
  |<== commands (targeted, full links, v5) ================================|
  |<== snapshot-chunk ===================|  (always ≥1 chunk, even empty)  |
  |=== snapshot-ack{chunks:1} ==========>|===============================>|  (v5: one ack per chunk)
  |<== snapshot-chunk … final:true ======|  (next chunks only as acks come) |
  |<== stream (targeted, if a reply is streaming) =========================|
  |<== ui-request × k (targeted, only writers, pending dialogs) ===========|
  |<== state (broadcast; participants changed) ============================|
  |<== live broadcast: entry/event/stream-delta/state/agents/bus … ========|
```

Order is guaranteed: the host builds the snapshot synchronously and enqueues welcome, the command list, the first window of chunks, baseline and ui-requests in that order (`CollabHost.#handleHello`). In v5 the remaining chunks follow the guest's acks, so live frames may interleave with them; buffer and apply them as in §4.4.

### 4.2 `hello`

The guest's first frame, and the first frame after **every** reconnect.

```json
{"t":"hello","proto":5,"name":"Pixel","history":"paged","writeToken":"oKGio6SlpqeoqaqrrK2urw"}
```

| Field | Type | Rule |
|---|---|---|
| `proto` | number | **Must equal the host's version** (`COLLAB_PROTO`, 5 since oms 18.20.3). On a mismatch the host replies with a targeted `error` reading `"protocol mismatch: host speaks vH, guest sent vN"` and no welcome. The Android guest sends 5 and, when H is 3 or 4, reconnects at once speaking H for the rest of that session; any other H is fatal |
| `name` | string | **Required.** A missing name throws on the host and no welcome is ever sent **(inferred, `host:976`)**. The host trims it and cuts it to 64 chars. Empty becomes `guest-<peerId>` |
| `history` | `"paged"` or omitted | `"paged"` requests a bounded latest page (≤100 entries / ~128 KiB). Omitted requests the **entire** transcript (`host:989-990`). **Recommended for Android: `"paged"`** |
| `writeToken` | string | base64url of the 16 token bytes. Omit for view links. Invalid or absent makes the peer read-only (`host:977`) |

Host-side pre-welcome refusals, each sent as a targeted `error` frame. A guest that receives an `error` before `welcome` must end the join and show the message (`wclient:658-666`, `nguest:399-408`):

- `"protocol mismatch: host speaks vH, guest sent vN"`
- `"Session transition in progress; join again when it completes"` (`host:960-962`). **(inferred)** It is safe to retry `hello` after a few seconds.

### 4.3 `welcome`

(`wire:367-383`, `host:996-1008`)

```json
{"t":"welcome","proto":5,
 "header":{"type":"session","version":3,"id":"…","title":"Fix login","timestamp":"2026-11-04T10:00:00.000Z","cwd":"/home/u/proj"},
 "state":{ …SessionState §5.6… },
 "agents":[ …AgentSnapshot §5.7… ],
 "entryCount":37,
 "readOnly":true,
 "history":{"beforeId":"e1f2a3b4","afterId":null,"total":512},
 "features":["models"]}
```

| Field | Meaning |
|---|---|
| `header` | Host `SessionHeader` (`wire:110-116`). It may carry extra keys such as `version`, `titleSource`, `additionalDirectories` and `parentSession` |
| `state` | Footer snapshot; see §5.6 |
| `agents` | Agent roster; see §5.7 |
| `entryCount` | Number of entries the following `snapshot-chunk` frames carry. In paged mode it is the page size, not the session total |
| `readOnly` | Present only as `true`, for view links or an invalid token. Absent means you can write |
| `history` | Present only when `hello.history == "paged"`. `total` is the count of all replicated entries in the host session |
| `features` | Optional host capabilities this peer may use, additive to `proto` (§5.2b). Absent means none. An oh-my-soup host lists `"models"` to full links only; stock oms sends no `features` |

On `welcome` (`wclient:469-510`):

- Reset everything: stream, active tools, bus maps, ui-request queue, history request.
- Set `working = state.isStreaming` and `readOnly = (readOnly == true)`.
- If `entryCount == 0`, the session is live immediately. Otherwise collect chunks.

### 4.4 `snapshot-chunk`

`{"t":"snapshot-chunk","entries":[SessionEntry…],"final":false|true}` (`wire:390`). The host's chunker is at `host:1178-1198`.

- Chunks are ~64 KiB each. A single oversized entry may travel alone, up to about 1 MiB.
- At least one chunk is always sent. For an empty snapshot that is `{"entries":[],"final":true}`.
- The snapshot is complete when `final == true` **or** the accumulated count reaches `entryCount` (`wclient:518-522`, `nguest:512`).
- Entries are the host's **active branch**, root to leaf, from just after its latest `/clear` boundary (`SessionManager.snapshotForReplication`), oldest first. Abandoned branches and the history a `/clear` dropped are not sent. (Hosts before this change sent every entry of every branch in file order; see §9.)

**Resync (mid-connection `welcome`).** When the active branch moves (a rewind or `/tree` move by the host or a guest, `/clear`, a discarded failed turn), the host sends every joined guest, on the same socket, the same sequence as at join: `welcome`, `commands` (writers), the snapshot chunks, the stream baseline and running tools, and the pending questions. It waits about 50 ms and until the session transition finished, and a guest command that moved the branch gets its `command-end` before that `welcome`. Handle it exactly like the `welcome` after a reconnect: keep showing the old view until the new snapshot is complete, then replace it; restart the `snapshot-ack` count; treat replayed `ui-request`s as replays. Hosts that predate this never send one, and a guest that never receives one behaves as before.
- Live `entry` frames may arrive while chunks are still pending. Buffer them and merge them after the snapshot, de-duplicating by `id` (`wclient:529-547`).

**Flow control (v5).** The host keeps at most about 1 MiB of unacknowledged chunks in flight per guest (`SNAPSHOT_WINDOW_BYTES`) and sends the next chunks only as the guest acknowledges earlier ones, because the relay bounds each guest's queue (the reference `oms-relay` queues 8 MiB per guest and closes one that falls further behind). **A v5 guest that never acks stalls its own join** after the first window, and then fails on the 30 s snapshot-gap timer.

```json
→ {"t":"snapshot-ack","chunks":3}
```

- Send one `snapshot-ack` after **every** `snapshot-chunk`, the empty final chunk of an empty snapshot included.
- `chunks` is cumulative: the number of `snapshot-chunk` frames received since the last `welcome`. Reset the count to 0 on each `welcome`.
- The host ignores stale, repeated and inflated counts (`CollabHost.#handleSnapshotAck`), and honours acks even during a provisional session switch.
- Never send it to a v4 or v3 host: they do not pace snapshots, and an unknown frame type is only logged.

### 4.5 Paged history (`fetch-history` / `history`)

```json
→ {"t":"fetch-history","reqId":12,"cursor":{"kind":"before","id":"e1f2a3b4"}}
← {"t":"history","reqId":12,"entries":[…],"page":{"beforeId":"9c0d…","afterId":"e0aa…","total":512}}
```

Cursors are **exclusive** and refer to entry ids (`host:1045-1102`, `wire:334-340`):

| cursor | entries (always oldest→newest) | `page.beforeId` | `page.afterId` |
|---|---|---|---|
| `{"kind":"latest"}` | newest entries | id of the oldest returned entry if older entries exist, else `null` | `null` |
| `{"kind":"before","id":X}` | entries strictly older than X | oldest returned id if more remain, else `null` | newest returned id |
| `{"kind":"after","id":X}` | entries strictly newer than X | oldest returned id | newest returned id if more remain, else **`null` = this page reaches the live tail** |

- **Bounds:** ≤100 entries and a soft 128 KiB of JSON, counting brackets and commas. The first entry is always included even if it is oversized (`wire:331-332`, `host:1078-1096`).
- **`total`** is the count of replicated entries.
- **Errors:** `error` is a string and `entries` is `[]`. The messages are:
  - `"Invalid history cursor"`
  - `"History cursor is no longer available; fetch latest history"`
  - `"Join before fetching history"`
  - `"Session transition in progress"`

  For the last two, `page` is `{null,null,0}` (`host:1027-1037,1051-1072`).
- **Browser rules:** one request in flight at a time, a 10 s timeout, and only send in the `live` phase (`wclient:311-324`). A reply with `afterId == null` means you are back at the live tail; merge any live entries that arrived meanwhile (`wclient:430-445,558-560`).
- Never send `before` when `beforeId == null`. An empty `before` page looks like the latest page **(inferred)**.

### 4.6 Live phase: typical frame order for one turn

Order verified against `host:741-766,518-535` and `agent-session.ts:3768-3792,3951-3962`.

```
event agent_start
event turn_start
event message_start {message.role:"custom", customType:"collab-prompt"}  (a guest prompt; a host prompt is role "user")
event message_end   (same)
entry custom_message (collab-prompt)     ← persisted asynchronously, normally AFTER the matching message_end event
state                                    (debounced 100 ms)
event message_start {role:"assistant", content:[]}
stream       {id:1, revision:0, message:{…}}   (first assistant update, coalesced 50 ms)
stream-delta {id:1, previousRevision:0, revision:1, patch}  … repeated
event message_end {role:"assistant", final message}
entry message (assistant)
event tool_execution_start / tool_execution_update* / tool_execution_end
event message_start/message_end (role "toolResult")
entry message (toolResult)
event turn_end
… more turns …
event agent_end
state {isStreaming:false}
```

- `message_update` events for the assistant are **never** sent as `event` frames. They become `stream` and `stream-delta` (`host:746-757`).
- While the agent runs, the host refreshes state every 2 s, and only sends it when it changed (`host:90,1386-1395,1521-1532`).

### 4.7 Read-only signalling

- `welcome.readOnly == true` for view links.
- `state.participants[i].readOnly == true` marks read-only guests (`host:354-360`).
- Read-only peers never receive `ui-request` (`host:410-416,1011-1016`).
- A mutating frame from a read-only peer gets a targeted `error` with `"<action> is disabled on a read-only link"`, where action is `prompting`, `interrupting`, `agent control`, or `responding to ask` (`host:935-937`).

### 4.8 Ending

| Signal | Meaning | Guest action |
|---|---|---|
| `{"t":"bye","reason":"…"}` | Host deliberately closed **this room**. Sent as a broadcast just before the host's socket closes (`host:576-600`) | End the session. Do **not** reconnect: the room id is dead (`wclient:655-657`, `nguest:710-714`) |
| close 4001 (+ TEXT `room-closed`) | Host's relay socket dropped. It usually comes back to the **same** room | Reconnect with backoff (§2.6) |
| close 4004 after a 4001 | Host not back yet | Keep retrying |
| decrypt failure | Wrong key or tampering | Fatal |

Known `bye` reasons:

| Reason | Source |
|---|---|
| `"host stopped"` (`/collab stop`, `/leave`) | `builtin-collaboration.ts:355,510` |
| `"host exited"` | `interactive-mode.ts:7542` |
| `"session switched; prompts not shown in the conversation were not submitted. Rejoin and resend them"` | `ctl:25-26` |
| `"restarting with control access"` | `ctl:174` |
| `"relay server changed; rejoin using the new link"` | `ctl:143` |
| `"replaced"` | `ctl:287` |
| `"joining another session"` | `builtin-collaboration.ts:481` |
| `"startup failed"` | `main.ts:803` |
| `"session changed before a guest prompt was submitted. Rejoin and resend any prompt not shown in the conversation"` | `host:1295-1297` |

**Room rotation:**

- `/new`, `/resume`, `/fork`, branching, and auto-start relaunches stop the room with `bye` and start a **new room with a new roomId and key** (`docs/collab.md:77,81`).
- There is no in-band redirect. A guest needs a new link.
- If the host's room ends without `stop()` (send backlog overflow, or a fatal relay close), **no `bye` is sent** (`host:466-470`). The host socket closes, so guests get `room-closed` + 4001, then 4004 on every retry, indefinitely **(inferred)**. With auto-start, the host creates a new room with a new link (`ctl` relaunch).

`prompt` details:

- When the host is idle, a prompt starts a turn. When it is busy, the prompt is queued as **steering**.
- It is persisted as a `custom_message` entry with `customType:"collab-prompt"` and `details:{from:<name>}`. The content is `text` alone, or `[{type:"text",text}, …images]` (`host:1254-1287`).
- Refused while the host is starting up: `"prompting is unavailable until the host finishes starting up"`. Refused during a session transition: `"… until the session transition completes"` (`host:944-951`).
- If the prompt was dropped: `"Prompt was not submitted. Please resend it when the host is ready."` (`host:1300-1303`).
- On failure: `"prompt failed: …"`.

`agent-cmd` details:

- `chat` requires non-empty `text`. It steers the subagent, reviving it if parked. `kill` aborts and releases it. `revive` revives it (`host:1427-1476`).
- Errors arrive as `error` frames with message `"agent <id>: …"`.

`transcript` details (v5; the Android app does not fetch subagent transcripts yet):

- `text` is whole JSONL lines from the first line start at or after byte `fromByte` of the subagent's session file, at most 256 KiB. A line too large to send is replaced by a short placeholder entry.
- Continue from `newSize`, which is a byte offset. Do not use `text.length`.
- The first line is the file's `{"type":"session",…}` header. Skip it.
- A present `error` is **terminal**. Show it and stop polling. Values include `"no transcript available"` and `transcript entry exceeds transcript fetch cap (4194304 bytes)`.
- The browser polls every 1.2 s and stops after 4 unchanged polls once the agent is not running (`AgentDrawer.tsx:17-19,67-120`).
- Raw transcript lines are **not** shrunk or filtered. They contain every entry type: `session_init`, `model_usage`, `label`, and so on.

`error` frames:

- Before `welcome`, an error is fatal to the join.
- After `welcome`, show it as an error notice (`wclient:658-668`).

### 5.2a Host commands (v5)

A guest holding a full link can run an allowlisted set of the host's slash commands. The host is the only enforcement point (`packages/coding-agent/src/collab/guest-commands.ts`, wired in `CollabHost.#handleCommand`); a view-only peer gets no command list and every request it sends is refused.

**Catalog.** Right after `welcome`, and again whenever the host's commands change, a full-control guest receives `{"t":"commands","commands":[…]}`. It comes before the first `snapshot-chunk`; a writer that sees a chunk without having received it can treat the list as empty (the host's command sources failed). Each `CollabCommand` is `{name, aliases?, description?, hint?, subcommands?:[{name, description?, usage?}], source}` with `source` one of `builtin|skill|custom|mcp_prompt|file|template`. `name` has no leading slash.

What a guest may run (`COLLAB_GUEST_HOST_BUILTINS`). Stock oms 18.20.x allows the first row only; this fork's host allows them all.

| Kind | Commands |
| --- | --- |
| Whole builtins (text handlers) | `/model`, `/switch`, `/effort`, `/fast`, `/slow`, `/skillful`, `/extended-context`, `/advisor`, `/ratchet`, `/prewalk`, `/jobs`, `/tools`, `/context`, `/compact`, `/shake`, `/retry`, `/rename`, `/dirs`, `/force`, `/heartbeat`, `/heartbeats`, `/btw <question>`, `/changelog`, `/fresh`, `/commit`, `/forget-approvals`, `/pin`, `/unpin`, `/handoff`, `/notes` |
| Rewind | `/rewind` (alias of `branch`), below |
| Listed subcommands only | `/todo` (bare, `copy`, `append`, `start`, `done`, `drop`, `rm`), `/modelpreset` (`list`, `switch`), `/session info`, `/memory view\|stats\|diagnose\|queue`, `/usage show`, `/sprompt` (bare, `toggle`, `clear`), `/security plan\|status\|scans\|show\|compare`, `/refine log`, `/mcp list\|resources\|prompts` |
| Screen commands (TUI handlers, see below) | `/plan`, `/vibe`, `/clear` (bare only), `/goal` (bare, `show`, `pause`, `resume`, `drop`, `budget`), bare `/modelpreset` (the preset picker) |

Plus skills, prompt templates, file slash commands, custom commands and MCP prompts. Everything else is host-only, including every command that replaces the session (`/new`, `/resume`, `/fork`, `/delete`, …), so a guest-run command never ends the room. The catalog lists only what a guest may run: a subcommand-limited builtin carries only its allowed `subcommands` and a hint such as `<list|resources|prompts>` (`[…]` when the bare command runs too); a refused subcommand ends `error` with a message naming the allowed ones. Builtins never open a dialog on the host's screen; `/model <selector>` and `/switch <selector>` take the model as an argument.

**`/rewind`.** Bare, it outputs the active branch's prompts, newest first, one per line as ``n. `entryId` text…`` (at most 10, text cut to 80 characters). `/rewind <n|entryId>` (a position from that list, or an entry id or unique id prefix; the entry id is the `id` of the prompt's `message`/`custom_message` entry, the Android `TranscriptItem.User.key`) rewinds past that prompt like the host's rewind selector: the leaf moves to the prompt's parent and the later turns stay as a branch. It is refused (`error`) while the agent is working. On success it sends two `command-output` blocks, a status line and then **the rewound prompt's text verbatim** (skill invocations kept as typed; images are not included), ends `done`, and the host resyncs every guest (§4.4).

**Screen commands.** These run the host's TUI handler for the asking guest: their status, warning and error lines come back as `command-output` (warnings and errors prefixed `Warning: ` / `Error: `; an error ends the command `error`), and their dialogs arrive as `ui-request`s sent to **that guest only** (§7.3): a selector as `select`, a yes/no confirmation as a `select` titled `title\nmessage` with the options `Yes` and `No`, a text prompt as `editor`. The command waits for the answer, so a question normally precedes the `command-end`. Nothing opens on the host's screen and the host's editor draft is never touched; mode changes (`/plan`, `/vibe`, `/goal`) show on the host as usual. A `/plan` or `/vibe` with a prompt argument is refused: it would be submitted as the host's own input.

**Running one.**

```json
→ {"t":"command","reqId":21,"text":"/effort low"}
← {"t":"command-output","reqId":21,"text":"Thinking set to low."}
← {"t":"command-end","reqId":21,"status":"done"}
```

- Every `command` gets exactly one `command-end`, refusals included, unless the room ends first. `status` is `done` (ran to completion), `prompt` (handed to the agent as a prompt; it continues in the transcript), `cancelled` (stopped by `command-cancel`) or `error` (`message` says why: read-only link, host still starting, session transition, host-only or unknown command, or the command failed).
- `command-output` frames carry Markdown for the asking guest only, at most 256 KiB each. A frame with `delta:true` continues the previous output without a break (a streaming `/btw` answer); otherwise it is a new block.
- `agentId` asks a subagent instead of the main session; only `/btw` accepts it.
- `{"t":"command-cancel","reqId":21}` stops a command still producing output. Unknown and finished requests are ignored.
- The host shows a notice naming the guest and the command, without its arguments; it reaches every participant as a `notice` event.

**Completions.** `{"t":"complete","reqId":22,"text":"/switch @sm"}` is always answered by one `{"t":"completions","reqId":22,"items":[{"value":"@smol","label":"@smol","description":"…"}]}`, at most 50 items. `value` replaces everything after the command name and its separating space. Only allowlisted builtins with argument completers answer with items (`/switch`, `/model`, `/effort`, `/fast`, …); everything else, and every view-only peer, gets `[]`.

## 6. Assistant stream (`stream` / `stream-delta`) and `applyCollabStream`

**Host side** (`host:741-874`):

- On assistant `message_start`, the host allocates `id = ++messageSeq` and sets `revision = -1`.
- Assistant `message_update`s are coalesced for 50 ms. The first emission is a full `stream` frame with `revision 0`.
- Each later emission is a `stream-delta` with `previousRevision = r` and `revision = r+1`.
- When the cumulative patch bytes would pass 1 MiB, or diffing fails, the host sends a fresh full `stream` frame with revision `r+1`.
- A guest joining mid-stream gets a targeted `stream` with the current revision. After a host reconnect, or after all peers have left, the next emission is a full baseline.
- `message_end` and `agent_end` end the stream.

**Guest state machine.** The browser version is the simpler one, at `wclient:573-600,714-729`:

```
on event message_start(role=assistant): baseline = null; ghost = event.message; done = false
on stream{id,revision,message}:        baseline = {id,revision,message}; ghost = message; done = false   // always accept
on stream-delta{id,previousRevision,revision,patch}:
    if baseline == null or baseline.id != id or baseline.revision != previousRevision or revision <= previousRevision:
        FATAL "Assistant stream lost synchronization. Rejoin…"   (end session; native: "rejoin the session")
    msg = applyCollabStream(baseline.message, patch) ?: FATAL "…patch could not be decoded…"
    baseline = {id, revision, msg}; ghost = msg; done = false
on event message_end(role=assistant):  baseline = null; ghost = event.message; done = true
on entry(message, role=assistant) when done: ghost = null; done = false   // committed row supersedes ghost
on state(isStreaming=false) when done: ghost = null
on (re)connect / welcome: baseline = ghost = null
```

The native guest is stricter: it requires `revision == previous.revision + 1` and the same `id` for a non-first baseline (`nguest:737-776`). Either behaviour works with the current host.

**`applyCollabStream(previous, patch)`** (`stream.ts:62-81`). Patch shape:

```
patch = { metadata: object /* every message field EXCEPT content */,
          contentLength: int,
          changes: [ {index, kind:"replace", value:any}
                   | {index, kind:"append", field:"text"|"thinking", offset:int, text:string, properties:object} ] }

applyCollabStream(previous, patch):
  content = copy of previous.content truncated to patch.contentLength   // never extended
  for change in patch.changes (in order):
     if change.index < 0 or change.index >= patch.contentLength: return null
     if change.kind == "replace":
         content[change.index] = change.value              // index may be == old size → appends
         continue
     before = content[change.index]                        // must be a JSON object
     old = before[change.field]
     if old is not a string or len16(old) != change.offset: return null
     content[change.index] = change.properties ∪ { change.field: old + change.text }   // properties REPLACE the other keys
  if content.size != patch.contentLength: return null
  if any content[i] is missing/undefined: return null
  return patch.metadata ∪ { content: content }             // metadata replaces ALL top-level fields
```

- **`offset` and `len16` are UTF-16 code-unit lengths.** These are JS `String.length` values. Kotlin `String.length` matches; byte counts and code-point counts do not.
- `replace` is used for new blocks, tool calls, and any non-append change.
- Key order in the result is not significant.

**Vector** (from `vectors/collab-vectors.out.txt`). The baseline content is `[{thinking:"Let me"},{text:"Hel"}]`, and the delta is:

```json
{"t":"stream-delta","id":1,"previousRevision":0,"revision":1,"patch":{"metadata":{"role":"assistant","api":"anthropic-messages","provider":"anthropic","model":"claude-x","usage":{…"output":9,"totalTokens":19…},"stopReason":"toolUse","timestamp":1730000000000},"contentLength":3,"changes":[{"index":0,"kind":"append","field":"thinking","offset":6,"text":" think","properties":{"type":"thinking","thinkingSignature":"sig1"}},{"index":1,"kind":"append","field":"text","offset":3,"text":"lo, world","properties":{"type":"text"}},{"index":2,"kind":"replace","value":{"type":"toolCall","id":"call_1","name":"read","arguments":{"path":"README.md"}}}]}}
```

The result has content `[{type:"thinking",thinkingSignature:"sig1",thinking:"Let me think"},{type:"text",text:"Hello, world"},{type:"toolCall",…}]` and `stopReason:"toolUse"`.

### 7.3 Host semantics

(`host:379-416,1200-1222`, `euc:930-955`)

- **First answer wins.** The host runs each dialog locally **and** mirrors it to every writable guest. The first answer settles it, whether from the host's keyboard or any guest. On settlement the host broadcasts `{"t":"ui-request-end","reqId":R}` to all writable peers. On receiving it, dismiss the request without responding.
- A `ui-response` for an unknown or already-settled `reqId` is answered with a targeted `ui-request-end` (`host:1218-1221`).
- After you send a response, advance your local queue immediately. Do not wait for `ui-request-end` (`wclient:277-283`).
- Several requests can be pending at once; the host caps them at 64. The browser shows them one at a time, FIFO, and `ui-request-end` removes queued ones (`wclient:634-641`).
- On `welcome`, clear all requests. The host **replays** pending requests to writers after each welcome, so they survive reconnects (`host:1011-1016,1332-1348`; `retainOnReconnect:true`, `euc:942,1104`).
- `confirm` and `input` extension dialogs are **not mirrored**; they are host-only (`euc:156-157`). Mirrored dialogs are `select`, `editor`, `approve` and `askDialog` (`euc:155-176`).
- **Targeted questions.** A screen command a guest runs (§5.2a) asks through the same frames, but only that guest receives the `ui-request`, its `ui-request-end` and its replay after a `welcome`, and only its answer settles it; another writer's `ui-response` for that `reqId` gets a targeted `ui-request-end`. No dialog opens on the host. The question is withdrawn (`ui-request-end`) when the command ends, is cancelled with `command-cancel`, or the guest leaves. Render it like any other pending request.

### 7.4 Tool approval

(`euc:675-760`, `approval:701-712,825-900`)

```json
{"reqId":9,"kind":"select","title":"Allow tool: bash\nReason: …\n<tool detail lines>…","options":["Approve","Approve bash for this session","Deny"]}
```

**`title`** is `prompt.full`: these lines joined with `\n`:

1. `Allow tool: <toolName>`
2. `Origin: MCP server tool`, for `mcp__*` tools without an explicit policy
3. `Reason: <reason>`, when one exists
4. The tool's own detail lines (command, path, content, …)
5. For directory grants, a folder block listing up to 24 entries
6. Any appendix, for example `Provider safety checks:`

Render it as preformatted text. It can be long.

**`options`**, in this exact order (`approval:876-885`):

| Option | When | Meaning (`approval:888-900`) |
|---|---|---|
| `"Approve Directory: <folder>"` | if offered | Grant for the folder, this session |
| `"Approve File"` / `"Approve"` (grant form) | if offered | Grant for the exact target(s), this session |
| `"Always Approve Directory: <folder>"` | if offered | Persistent folder grant |
| `"Always Approve File"` / `"Always Approve"` | if offered | Persistent target grant |
| `"Approve Once"` when grants exist, otherwise `"Approve"` | always | Allow this call only |

The same applies to a host-typed message. **(inferred)** A pending `ask` is *not* cancelled by steering; the prompt is delivered after the tool finishes.

### 7.5 The `ask` tool

(`euc:765-791,957-1108`; tool side `packages/coding-agent/src/tools/ask.ts:768-803`)

The local multi-question dialog is mirrored as a **sequence of separate requests**, one or more per question, in question order. Each step has a new `reqId`.

Sentinel option labels (`euc:61-63`), copied exactly:

| Label | Meaning |
|---|---|
| `"Other (type your own)"` | Opens an editor for a custom answer |
| `"Chat about this"` | Abandons the whole ask. The tool returns "User chose to chat about this instead of answering." |
| `"Next →"` (U+2192) | Multi-select only: finish this question |

Real option labels are made unique and sentinel-safe. A label that collides with a sentinel or another label gets a suffix ` (2)`, ` (3)`, … and carriage returns are normalized (`packages/tui/src/render/render-utils.ts:50-59`). Echo the displayed label exactly; the host maps it back.

**Single-select question:**

```json
{"reqId":20,"kind":"select","title":"<question>","options":["Opt A",{"label":"Opt B","description":"…"},"Other (type your own)","Chat about this"],
 "initialIndex":<recommended clamped, default 0>,"selectionMarker":"radio","markableCount":<n real options>,"helpText":"…"}
```

| Response value | Result |
|---|---|
| a real label | Answer recorded; next question |
| `"Chat about this"` | Ask ends as "chat" |
| `"Other (type your own)"` | Host sends an editor request: `{"kind":"editor","title":"Custom answer: <question>"}`. The title is wrapped to the host terminal width with `\n` and cut to 3 rows ending in `…` (`packages/tui/src/overlays/hook-editor.ts:58-67`) |
| → editor text submitted | Becomes `customInput`; next question |
| → editor cancelled | The same select is re-sent with a new `reqId` |
| cancel (no value) | **Cancels the entire ask**: `ToolAbortError("Ask tool was cancelled by the user")`, plus `context.abort()`, which aborts the agent's current operation (`ask.ts:788-791`) |

**Multi-select question:** a loop, one request per toggle.

```json
{"reqId":21,"kind":"select","title":"<question>","options":["A","B","C","Other (type your own)","Next →","Chat about this"],
 "selectionMarker":"checkbox","checkedIndices":[0,2],"markableCount":3,"helpText":"…"}
```

| Response value | Result |
|---|---|
| a real label | **Toggles** that option. The host re-sends the select with a new `reqId` and updated `checkedIndices` |
| `"Next →"` | Finishes the question. **`Next →` only appears once at least one option is checked or a custom answer exists** |
| `"Other (type your own)"` | Opens the editor. Submitting sets `customInput` **and finishes the question**; cancelling returns to the list |
| `"Chat about this"` | Ask ends as "chat" |
| cancel | Cancels the whole ask, as for single-select |

There is no image support in guest custom answers. The local host dialog accepts images; the guest editor carries text only.

## 8. How collab-web renders (match this on Android)

Sources: `packages/collab-web/src/components/transcript/Transcript.tsx`, `components/shell/{Composer,HeaderBar}.tsx`, and `wclient:714-795`.

**Transcript rows**, in entry order (`Transcript.tsx:197-285`):

| Entry | Rendering |
|---|---|
| `message` / `user` | User bubble with gutter "host"; Markdown text plus inline images |
| `message` / `assistant` | Blocks in order. `thinking` is a collapsed "thinking" toggle that expands to raw text. `redactedThinking` shows "thinking · redacted". `text` is Markdown. `toolCall` is a tool card. If `stopReason` is `error` or `aborted`, a chip plus `errorMessage` follows |
| `message` / `toolResult` | **Hidden when its `toolCallId` matches a toolCall in the visible window** (it is folded into that card). Otherwise it is a standalone tool card |
| `message` / any other role | Hidden (developer, bashExecution, pythonExecution, fileMention, …) |
| `custom_message` with `collab-prompt` | User bubble with a badge showing `details.from` (default "guest") |
| `custom_message` with `display:true` | Row with a `customType` chip plus the content |
| `custom_message` with `display:false` | Hidden |
| `compaction` | Divider: "context compacted · N tokens" (`tokensBefore`) |
| `branch_summary` | Divider: "branch summary" |
| `model_change` | Marker: "model → provider/id" |
| `thinking_level_change` | Marker: "thinking → level" (`off` when null) |
| unknown | Skipped |

**Tool grouping** (`Transcript.tsx:122-150,336-454`):

- A tool card combines the toolCall `name`, its `arguments`, the matching `toolResult` message, and the live `ActiveTool` from `tool_execution_*`.
- While running, the card shows `partialResult` text: the joined `content[].text` (`format.ts:73-97`).
- `ActiveTool` entries not referenced by any committed or streaming toolCall render in a trailing row.
- A committed toolCall that has no result, is not active, and is not streaming shows "Result not on this page."
- Per-tool renderers are keyed by tool name (bash, read, edit, write, grep, glob, task, todo, ask, web_search, …), with a generic JSON fallback (`tool-render/registry.ts`).

**Live tail:**

- After the entries, show the stream ghost (§6) while it exists. Text uses streaming Markdown until `done`.
- Show a "thinking…" shimmer while `working`, with no ghost and no active tools (`Transcript.tsx:502-533`).
- `working` comes from `agent_start`/`agent_end` and is overridden by every `state.isStreaming`.

**Notices** become toasts, keeping at most 50 (`wclient:767-790`):

| Source | Toast text |
|---|---|
| `notice` event | its message |
| `auto_retry_start` | `retry a/b: <errorMessage>` |
| `auto_retry_end` with `!success` | `finalError` |
| `auto_compaction_start` | `compacting context (<reason>)` |
| `auto_compaction_end` with `!skipped` | `compaction aborted`, or `compaction failed: …`, or `context compacted` |
| `error` frame after welcome | its message |

`turn_*`, `thinking_level_changed` and `agent_end` payloads are ignored.

**Header** (`HeaderBar.tsx:40-100`) shows:

- Title: `header.title ?? state.sessionName ?? "session"`
- The shortened `state.cwd`
- `model.name` and `thinkingLevel` chips
- Context %
- Participants, with read-only guests marked

**Composer** (`Composer.tsx:120-264`):

- Enabled only when the phase is live and the guest is not read-only. Text is trimmed before sending.
- A Stop button (sends `abort`) appears while working.
- A "queued ×N" badge appears when `queuedMessageCount > 0`.
- A pending `ui-request` **replaces** the composer. It shows the title, option buttons (with markers), or an editor with Submit, plus Cancel and Stop.

**Windowing:**

- The browser keeps at most 100 entries and 128 KiB live (`wclient:132-154`), with Older/Newer/Latest navigation via `fetch-history`.
- Historical pages hide the live ghost and active tools (`app.tsx:160-214`).

## 9. Gaps and gotchas for a native guest

1. **The transcript is a tree, sent as the active branch.**
   - Entries carry `parentId`. Snapshots and history pages hold the active branch only (§4.4), and the host resyncs guests when it moves, so rendering them linearly is correct.
   - Live `entry` frames are appends; an entry appended off the active branch (rare: background work on another branch) still arrives and shows until the next resync.
   - Hosts before the resync change sent all branches in file order and never resynced: abandoned branches showed inline until a rejoin.
2. **Shrunk payloads.** Any entry, event or stream message over 1 MiB (UTF-8 JSON) is progressively shrunk (`shrink:55,103-111,114,169-173,212-235`):
   - Strings are cut and suffixed `\n…[N chars elided for collab session]`. **This can corrupt base64 image `data`**, so validate before decoding.
   - Arrays are cut and get a trailing **string** element `…[N items elided for collab session]`, so content arrays can contain a non-object.
   - Deep nesting becomes `"…[deeper levels elided for collab session]"`.
   - If shrinking fails, entries become `collab-entry-too-large` placeholders and events become `notice`s.
   - Full snapshots over 24 MiB have their images stripped (`host:92,1139-1167`).
3. **Not mirrored:**
   - `confirm`/`input` dialogs.
   - Events not in §5.5: no `queue_update` (so no list of queued messages, only a count), no `tool_stream_update`, no goal/todo events.
   - Entry types other than the six in §5.4.
   - Host slash commands outside the guest allowlist (§5.2a). Before v5 no host command was guest-runnable.
   - Image paste in ask custom answers.
4. **Mid-turn join.**
   - Tools already running at join time are not replayed as `tool_execution_start`, so they appear without a running state until their result entry lands **(inferred)**.
   - The in-flight assistant message *is* replayed, as a targeted `stream` baseline.
   - The welcome `state.isStreaming` tells you a turn is in progress.
5. **Event versus entry ordering.**
   - The `message_end` event normally precedes the matching `entry` frame, because persistence is queued asynchronously **(inferred, `agent-session.ts:3951-3962`)**.
   - Use the browser's rule: an assistant `entry` clears the ghost only after `message_end`, and `state.isStreaming=false` clears a finished ghost.
   - De-duplicate entries by `id`.
6. **No in-band session follow.** A `bye` means the room is gone for good. Session switches create a new room id and key, so the user must rescan or repaste.
7. **Reconnect identity.**
   - Each reconnect gets a new peer id. Permissions bind on `hello`.
   - Never send mutating frames before the new `welcome` (§2.6).
   - Pending ui-requests are replayed after the welcome.
   - A `ui-response` sent just before a drop may be lost. Re-answer the replayed request.
8. **Startup gating.** Right after a host starts (auto-start), prompts, aborts and agent commands get the `error` `"… is unavailable until the host finishes starting up"`. Answering `ui-request`s still works (`host:179-190,944-951`).
9. **Size limits.**

   | Item | Limit |
   |---|---|
   | Host payload cap | 1 MiB per replicated payload |
   | Snapshot chunks | ~64 KiB |
   | History pages | 100 entries / ~128 KiB |
   | Transcript replies | ≤ 4 MiB |
   | Relay per-frame cap | 2 MiB per WebSocket message, envelope included (`COLLAB_RELAY_MAX_MESSAGE_BYTES`); the reference `oms-relay` closes a connection that sends more with 1009 |
   | Command output | 256 KiB per `command-output` frame, and per request for a streamed `/btw` answer |

   **(inferred)** Keep guest `prompt` frames, including base64 images, well under 1 MiB. The prompt entry is re-broadcast to every guest, and over 1 MiB it is shrunk, which corrupts the images.
10. **Host backlog.** If the host's send queue passes 256 frames or 16 MiB, the **room ends** (`rc:60-61,306-311`). Slow guests on poor networks can contribute. Read promptly, and do not stall the socket thread on UI work.
11. **Name and identity.** The display name is self-asserted and limited to 64 chars. The relay sees room ids, frame sizes and peer routing, never content.
12. **Transcript fetch.** Offsets are **bytes** in the host file. `text` is decoded UTF-8 cut at a newline, so reuse `newSize`. Rows are raw, unshrunk JSONL that includes non-wire entry types. Skip `type:"session"` and unknown types.
13. **Cancel is not neutral for `ask`.** Cancelling an ask question aborts the host agent's current operation. Offer "Chat about this" as the soft exit.
14. **Steering denies approvals.** Sending a prompt while an approval is pending denies that approval (§7.4).
15. **UTF-16 offsets** in stream patches (§6).
16. **Browser bugs not to copy:** it flushes buffered frames before `hello` (§2.6), and it has no idle keepalive.
17. **The local registry is not reachable remotely.** `oms collab list` and `oms collab link` are a local-machine IPC socket. Links reach a phone only through QR codes, copy, or another channel.
18. **Unknown/production-only details:** the real relay (`oms-relay`, Rust, kept on another branch) is not in this repo. Its room capacity (4029), payload cap, idle timeout and `Origin` policy are unspecified here. The reference relay `packages/collab-web/scripts/local-relay.ts`, run with `bun run collab:relay` (`ws://localhost:7466`), implements the routing contract described above and is the right target for testing.
